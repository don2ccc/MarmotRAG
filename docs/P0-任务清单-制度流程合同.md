# P0 任务清单：制度 / 流程 / 合同知识库

> 主语料已确认：**制度、流程、合同**。
> 本文档把 [RAG-诊断与改进路线图](./RAG-诊断与改进路线图.md) 收敛为可排期的 P0 清单。
> 假设 1 名熟悉本仓库的后端开发，5 个工作日/周，总计约 **17 人日（3.5 周）**。

---

## 0. 语料特征如何改写优先级

| 语料特征 | 直接后果 | 优先级变化 |
|---|---|---|
| **版本决定对错**（制度有修订、合同有补充协议） | 召回旧版比召回不全更严重：会给出错误答案且看起来有理有据 | 版本管理 **P1 → P0** |
| **条款是天然引用单元**（第 12 条 / Article 5.2） | 用户与审计要的是"第几条"，不是"某段文本" | 条款级 chunk + 条款级 citation **→ P0** |
| **合同 80% 是模板化条款** | 同一句话在几十份合同里重复，top-k 被模板文本占满 | 近重复抑制 **→ P0** |
| **时效性强**（生效/废止/到期） | 已废止制度仍在库里平等参与排序 | 默认只召回有效版本 **→ P0** |
| **范本 vs 已签并存** | 问"我方违约金上限"，召回的是空白范本 | `doc_kind` 过滤 **→ P0** |
| **层级与适用范围**（集团制度 > 子公司办法 > 部门细则） | 多条同时命中，无法判断哪条适用 | 元数据 + 冲突标记 **→ P1** |
| **审批矩阵/费率表是表格** | 拍平后金额与审批人错位 | 表格感知 **→ P1** |
| **中英双语合同** | 单语向量跨语言召回弱 | **P2** |

**一句话**：对制度/合同，**"召回得对不对"的核心矛盾不是语义相似度，而是"是不是现行有效的那一版、有没有引用到条款"**。所以先把版本与时效做对，再谈混合检索。

## 1. P0 完成后的系统行为（验收基线）

六条，全部可自动化验证：

1. **重索引期间检索不中断** —— 重建 10 分钟内，该源仍以旧版本正常召回。
2. **重建失败不丢知识** —— 故意注入嵌入失败，旧版本继续服务，`last_error` 可见。
3. **能回答"哪一版"** —— 每个返回块可定位到 `文档 / 版本号 / 生效日期 / 条款号 / 页码 / 字符区间`。
4. **废止即不召回，但可回溯** —— 已失效文档默认不出现；带 `asOf` 可查到"当时生效"的版本。
5. **重复入库不重复召回** —— 同一内容以不同 id 入库两次，top-5 里只出现一份。
6. **数字可信** —— `token_count` 与实际分词一致；无"向量只覆盖前 2000 字"的隐式截断。

## 3. 数据模型变更（P0 最小集）

只加 P0 需要的字段，不做全量重构。

```sql
-- 新增：文档（逻辑实体，对外稳定身份）
CREATE TABLE marmot_docs (
  id                 TEXT PRIMARY KEY,
  name               TEXT NOT NULL,
  kind               TEXT NOT NULL DEFAULT 'policy',   -- policy|process|contract|template|annex
  doc_no             TEXT,                              -- 文号 / 合同编号
  owner_id           TEXT NOT NULL,
  department         TEXT,                              -- 适用范围（P1 用）
  is_shared          BOOLEAN NOT NULL DEFAULT FALSE,
  current_version_id TEXT,
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 新增：版本
CREATE TABLE marmot_doc_versions (
  id                 TEXT PRIMARY KEY,                  -- ver_<ulid>
  doc_id             TEXT NOT NULL REFERENCES marmot_docs(id) ON DELETE CASCADE,
  version_no         INTEGER NOT NULL,
  content_sha256     TEXT NOT NULL,
  lifecycle          TEXT NOT NULL DEFAULT 'effective', -- draft|effective|expired|revoked
  effective_from     TIMESTAMPTZ,
  effective_to       TIMESTAMPTZ,
  signed_at          TIMESTAMPTZ,                       -- 合同专用
  amends_version_id  TEXT,                              -- 补充协议指向被修订版本（P1 用）
  index_state        TEXT NOT NULL DEFAULT 'building',  -- building|active|failed|stale
  last_error         TEXT,
  chunk_strategy_hash TEXT NOT NULL,
  embedding_model    TEXT NOT NULL,
  chunk_count        INTEGER NOT NULL DEFAULT 0,
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (doc_id, version_no)
);

-- 扩展：chunks（保留原表，ALTER 加列，避免一次性重写）
ALTER TABLE marmot_chunks
  ADD COLUMN IF NOT EXISTS version_id        TEXT,
  ADD COLUMN IF NOT EXISTS doc_id            TEXT,
  ADD COLUMN IF NOT EXISTS ordinal           INTEGER,
  ADD COLUMN IF NOT EXISTS clause_no         TEXT,      -- "第12条" / "5.2"
  ADD COLUMN IF NOT EXISTS clause_path       TEXT,      -- "第12条 > 第2款"
  ADD COLUMN IF NOT EXISTS page_from         INTEGER,
  ADD COLUMN IF NOT EXISTS char_start        INTEGER,
  ADD COLUMN IF NOT EXISTS char_end          INTEGER,
  ADD COLUMN IF NOT EXISTS content_sha256    TEXT,
  ADD COLUMN IF NOT EXISTS embed_input_chars INTEGER;

CREATE INDEX IF NOT EXISTS marmot_chunks_version_idx ON marmot_chunks (version_id);
CREATE INDEX IF NOT EXISTS marmot_chunks_trgm_idx
  ON marmot_chunks USING gin (text gin_trgm_ops);
```

**迁移策略**（必须幂等、可回滚）：
1. 为每个存量 `marmot_sources` 建一条 `marmot_docs` + 一条 `marmot_doc_versions(version_no=1, lifecycle='effective', index_state='active')`；
2. `UPDATE marmot_chunks SET version_id=..., doc_id=..., content_sha256=md5(text)`；
3. 校验：`SELECT count(*) FROM marmot_chunks WHERE version_id IS NULL` = 0，否则回滚；
4. 检索改为 join `marmot_docs.current_version_id`，旧 `marmot_sources` 保留一个版本周期后再删。

**切换语义**（T1 的核心）：
```sql
BEGIN;
UPDATE marmot_doc_versions SET index_state='active'  WHERE id = $new;
UPDATE marmot_doc_versions SET index_state='stale'   WHERE doc_id = $doc AND id <> $new AND index_state='active';
UPDATE marmot_docs SET current_version_id = $new, updated_at = now() WHERE id = $doc;
COMMIT;
```
失败时只写 `index_state='failed', last_error=...`，`current_version_id` 不动 → **旧知识继续服务**。

## 4. 条款感知切分规则（制度/合同）

按优先级从高到低匹配分割点，命中即切：

1. **条**：`第[一二三四五六七八九十百零〇\d]+条`、`Article\s+\d+`、`第\s*\d+\s*章`（章作为 `heading_path` 前缀）
2. **款**：`（[一二三四五六七八九十]+）`、`\([a-z]\)`、`\d+\.\d+`
3. **项**：`\d+）`、`[（(]\d+[）)]`
4. **段落**：连续两个换行
5. **句子**：`[。；！？;]`

约束：

- **一条不跨块是硬约束**；单条超过目标长度时，按"款 → 项 → 句"逐级降级切分，且每块保留同一 `clause_no`，块首加 `（续）`。
- **前置上下文**：每块首行注入 `clause_path`（如 `【第12条 第2款】`），保证块独立可读。
- **表格整块保留**，并在每块重复表头（审批矩阵、费率表、违约金表）。
- **目录/页眉/页脚/页码**在解析阶段剥离，不入库（否则目录条目会与正文争 top-k）。
- **附件/附录**单独成块，`kind='annex'` 标记。
- **范本与已签合同**用 `kind` 区分，检索默认排除 `template`。

块大小建议（制度/合同）：目标 **300–500 字**、重叠 **0 字**（条款边界清晰，重叠反而制造重复召回）；只有被迫降级到句子级切分时才启用 10% 重叠。

## 5. 检索默认语义变更

```
默认条件：
  d.current_version_id IS NOT NULL
  AND v.index_state = 'active'
  AND v.lifecycle = 'effective'
  AND (v.effective_to IS NULL OR v.effective_to > now())
  AND (d.owner_id = $user OR d.is_shared)
  AND d.kind <> 'template'        -- 除非 filters.kinds 显式包含
```

`asOf=T` 时把 `effective_from <= T AND (effective_to IS NULL OR effective_to > T)` 作为版本选择条件，忽略 `current_version_id`。

**这条改动本身就是"制度问答不出错"的最大来源**——比任何打分调优都有效。

## 7. 验收测试集（P0 必须建）

放在 `scripts/eval/`，JSONL，每条 `{query, expect:{docId, clauseNo?}, asOf?, must_not?:[...]}`。

| 组 | 条数 | 覆盖什么 |
|---|---|---|
| 时效题 | 20 | "现行版怎么规定" vs "旧版怎么规定"；废止文档不得出现 |
| 条款定位 | 15 | "第几条规定了…"；`clauseNo` 必须精确命中 |
| 废止隔离 | 10 | 已 `revoked/expired` 的文档，默认召回中必须为 0 |
| 范本 vs 已签 | 10 | 问"我方违约金"，不得返回空白范本 |
| 重复抑制 | 10 | 同内容双入库，top-5 无重复 |
| 字面命中 | 10 | 完整文号 / 合同编号 / 条款号 → top-3 |

**门禁指标**：`recall@5 ≥ 0.80`、`陈旧率 = 0`、`重复率 ≤ 0.2`、`p95 ≤ 300ms`。任何后续改动（切分/模型/权重）跑这套，退步 > 2% 阻断。

## 8. P0 明确不做

- ❌ 冲突裁决 / 合规推理（"哪条优先适用"）——这是 Agent 或人的职责，R 只提供层级与时效元数据
- ❌ 合同条款抽取成结构化字段（金额、期限、违约金）
- ❌ 补充协议链自动合并（P1）
- ❌ 中英双语对齐
- ❌ 多租户 / 部门级 ACL（先靠 `is_shared` + `kind`）
- ❌ rerank 模型（先 MMR，看评估结果再决定）

## 9. P1 预告（做完 P0 再谈）

1. **补充协议感知检索**：`amends_version_id` 链，检索时自动带上仍有效的修订，并在引用里标"已被 X 修订"。
2. **审批矩阵结构化**：流程文档里的"金额区间 → 审批人"表抽成 lookup，提供 `/lookup` 或作为 chunk 的强类型元数据。
3. **层级与适用范围**：`hierarchy_level`（集团/子公司/部门）+ `applicable_scope`，检索返回时并列给出，冲突由调用方裁决。
4. **冲突标记**：同一 `clause_no` 主题下多条并列命中时，`diagnostics.conflicts[]` 提示。
5. **双语对齐**：同一 `doc_id` 的 zh/en 版本共享 `current_version_id`，检索任一侧可回溯另一侧。

### A.5 已知限制

1. **近重复检测用 3-gram Jaccard**，不是向量相似度；对"改几个字"的模板条款有效，对深度改写无效。
2. **词法通道是标识符驱动**：只抽取文号/料号/条款号/长数字。自然语言长句仍靠向量通道。
3. **as-of 受版本保留策略限制**（默认 5 版），不是完整时间机器。
4. **条款识别是正则**：非标准编号（纯缩进、"1)"样式）会回退到句子切分，此时不产生 clauseNo。
5. **MMR 复杂度 O(k·n)**，候选池默认 ≤200，对万级文档足够；更大规模需换近似多样性。
